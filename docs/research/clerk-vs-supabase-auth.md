# Clerk × Supabase Auth para o login do WaPilot

Pesquisa em 12/11/2026. Fontes externas: documentação e preços oficiais consultados nesta data. Esta comparação trata da substituição do **Cloudflare Access no login do navegador**; o Worker, D1 e `@cloudflare/workers-oauth-provider` podem continuar. As consequências para o WaPilot são inferências do [código de autenticação](../../src/lib/auth.ts), [OAuth](../../src/lib/oauth.ts), [usuários](../../src/lib/db.ts) e [rotas](../../src/index.ts), não promessas dos fornecedores.

Se “substituir Cloudflare” significar eliminar **todo** componente Cloudflare da autenticação, nenhuma das duas opções abaixo basta sozinha: o emissor OAuth do MCP ainda é o pacote Cloudflare, com estado em KV. Isso seria uma segunda migração, além da troca de login ([Worker atual](../../src/worker.ts), [OAuth atual](../../src/lib/oauth.ts)).

## O que a troca precisa preservar

`/connections`, `/admin`, `/api` e `/authorize` hoje recebem identidade do Access. `/authorize` cria grants do OAuth Provider com `userId = encodeURIComponent(email)` e `props.user`; `/mcp` recebe apenas o bearer desse Provider. O D1 guarda conexões pelo UUID interno do usuário, encontrado hoje por e-mail. A troca do serviço de login deve preservar as linhas D1 e os grants existentes, verificar conta `active` em cada entrada protegida e impedir a criação automática de contas por `ensureUser`. A identidade autenticada no Clerk/Supabase **não** deve virar bearer aceito em `/mcp`. Veja também a [pesquisa anterior](external-user-auth.md).

## Migração que ambos exigem

1. Criar contas de Lucca e Heitor no provedor escolhido; ligar seus identificadores `sub` às linhas `users.id` **existentes**, sem regravar conexões. Manter o e-mail normalizado que hoje identifica os grants do OAuth Provider; mudança de e-mail exige migração explícita dos vínculos. Essa é uma inferência do [schema D1](../../migrations/0001_init.sql) e do [OAuth atual](../../src/lib/oauth.ts).
2. Trocar a verificação Access de `/authorize`, `/connections`, `/admin` e rotas API por sessão validada no Worker. Nas duas opções, verificar `users.status = 'active'` **antes de emitir grants** e **em cada request `/mcp`**, inclusive com grants antigos. Preservar a allowlist administrativa separada. Remover a criação implícita de usuários em requests comuns. Veja [auth.ts](../../src/lib/auth.ts), [db.ts](../../src/lib/db.ts), [oauth.ts](../../src/lib/oauth.ts) e [index.ts](../../src/index.ts).
3. Preservar `@cloudflare/workers-oauth-provider` para `/mcp` no primeiro corte: só muda a autenticação do navegador em `/authorize`. O [OAuth Server do Supabase](https://supabase.com/docs/guides/auth/oauth-server/getting-started) já documenta MCP e registro dinâmico, mas está **em beta**; migrar o emissor de tokens mudaria descoberta, issuer, audience, clientes, consentimento, grants, refresh e revogação. Não há evidência nesta pesquisa de compatibilidade integral com o contrato MCP `2026-07-28` fixado pelo WaPilot ([guia MCP do Supabase](https://supabase.com/docs/guides/auth/oauth-server/mcp-authentication), [arquitetura local](../ARCHITECTURE.md)).
4. Manter respostas autenticadas sem cache compartilhado. Em especial, se usar `@supabase/ssr`, aplicar os headers de `Set-Cookie`/`Cache-Control` que o helper entrega; a documentação alerta que cache CDN de resposta com cookie pode autenticar outra pessoa ([guia avançado](https://supabase.com/docs/guides/auth/server-side/advanced-guide)). Testar conta não convidada, desativada, sessão expirada, token MCP anterior ao bloqueio e vínculo com conexões existentes.

## Decisão para este projeto

**Clerk é a melhor escolha se o objetivo é substituir Access rapidamente com convites e login por e-mail gerenciados, mantendo a UI atual e o OAuth MCP.** O fluxo hospedado e a verificação de sessão em Workers/Hono diminuem o trabalho próprio; o custo de Pro só se justifica se MFA/passkeys ou política de sessão customizada forem requisitos de produção. [Convites](https://clerk.com/docs/guides/users/inviting), [Workers/Hono](https://clerk.com/articles/authentication-for-serverless-and-edge-deployments-2), [preços](https://clerk.com/pricing).

**Supabase Auth é preferível se TOTP gratuito, controle da entrega de e-mail ou stack Auth local forem prioridades e a equipe aceitar SMTP e o ciclo de cookies/refresh.** Usá-lo apenas para Auth deixa um Postgres/serviço adicional sem substituir D1 nem o OAuth Provider. [TOTP](https://supabase.com/docs/guides/auth/auth-mfa/totp), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [sessão no servidor](https://supabase.com/docs/guides/auth/choosing-a-server-package).

Não foram inspecionados planos contratados, configuração de produção, entregabilidade real de e-mail nem fluxo end-to-end com clientes MCP. Nenhuma infraestrutura ou código foi alterado.
