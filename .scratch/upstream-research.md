## Protocolo MCP publicado mais recente

A especificação publicada mais recente em 2026-10-13 é [`2026-07-28`](https://modelcontextprotocol.io/specification/2026-07-28). Ela define requests autocontidos e negociação por requisição. O transporte Streamable HTTP expõe um único endpoint POST, com uma requisição JSON-RPC por POST; GET para stream independente, `Mcp-Session-Id`, DELETE de sessão e o transporte HTTP+SSE legado foram removidos nessa revisão ([transporte](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). O endpoint alvo deve ser `/mcp`. O servidor precisa validar `Origin`, `MCP-Protocol-Version`, `Mcp-Method` e `Mcp-Name`; respostas podem ser JSON ou SSE limitado à requisição. O transporte legado HTTP+SSE está depreciado desde 2025-03-26 e não deve ser implementado.

A autorização 2026-07-28 exige que MCP HTTP use OAuth 2.1 (PKCE S256 para clientes públicos), Protected Resource Metadata (RFC 9728), descoberta de authorization server, Resource Indicators (RFC 8707), validação de audience e respostas 401/403 adequadas ([autorização](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). A documentação de Cloudflare confirma `/mcp` com Streamable HTTP stateless para servidores remotos ([Cloudflare MCP](https://developers.cloudflare.com/agents/model-context-protocol/cloudflare/servers-for-cloudflare/)).

## Comparação dos MCPs existentes

### evolution-foundation/mcp-evolution-api

* `src/index.ts` registra 20 tools (`getApiStatus`, `getInstanceStatus`, `setPresence`, `logoutInstance`, `restartInstance`, `sendTextMessage`, `sendMedia`, `sendAudio`, `sendSticker`, `sendLocation`, `sendContact`, `sendPoll`, `checkWhatsAppNumber`, `markMessageAsRead`, `archiveChat`, `deleteMessageForEveryone`, `updateProfileName`, `updateProfileStatus`, `createGroup`, `addGroupParticipants`) e 5 resources (`contacts://list`, `chats://list`, `groups://list`, `profile://info`, `privacy://settings`). Schemas são Zod, mas a maior parte das respostas é apenas texto interpolado, por exemplo o ID da mensagem.
* `EvolutionApiService` usa Axios com um único `EVOLUTION_API_URL`, `EVOLUTION_API_KEY` e `EVOLUTION_API_INSTANCE` no processo. O header global `apikey` é aplicado a todas as rotas. Não há usuário, isolamento entre conexões, seleção por ID interno, paginação, webhook de recebimento ou download de mídia.
* O cliente contém vários métodos não expostos como tools (por exemplo `findMessages`, `fetchContacts`, `fetchChats`, métodos de grupo, perfil e integrações). `findMessages` não tem paginação; não existe ferramenta de histórico.
* O entrypoint inicia `StdioServerTransport` sempre e, opcionalmente, `WebSocketServerTransport` com `ws`/HTTP Node. Não existe Streamable HTTP; o WebSocket e o estado de um `McpServer` compartilhado não são compatíveis com o alvo Worker stateless.
* `package.json` fixa apenas ranges (`@modelcontextprotocol/sdk ^1.8.0`, Axios, Zod, `ws`) e o script `test` falha intencionalmente (“no test specified”). Não há testes de integração, OAuth, controle de acesso ou validação de respostas.
* Aproveitar: nomenclatura de intenções, alguns schemas básicos de envio e a ideia de resources. Adaptar: tudo para contratos Evolution Go e respostas estruturadas. Descartar: transporte stdio/WebSocket, singleton com instância por ambiente, administração destrutiva e mensagens de erro que vazam detalhes.

## Evolution Go: contrato efetivamente implementado

A fonte de rotas é [`pkg/routes/routes.go`](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/pkg/routes/routes.go); o OpenAPI correspondente é [`docs/swagger.json`](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/docs/swagger.json). O checkout analisado declara `VERSION=0.7.2`, módulo Go 1.25 e commit `9337afc`; isso identifica a versão do código upstream, não confirma a versão implantada do servidor do usuário. Não havia `EVOLUTION_API_URL`, chave ou token no ambiente para uma chamada controlada; portanto a versão implantada e contratos de uma instalação concreta permanecem pendentes.

### Autenticação e isolamento

* `GLOBAL_API_KEY` é exigida no header `apikey` para rotas administrativas: `POST /instance/create`, `GET /instance/all`, `GET /instance/info/:instanceId`, `DELETE /instance/delete/:instanceId`, proxy, force-reconnect e logs.
* O token específico da instância também é enviado no mesmo header `apikey` para rotas WhatsApp. Ele resolve a instância no backend; não há `instanceName` na URL dessas rotas. Exemplos: `GET /instance/status`, `GET /user/contacts`, `GET /group/list`, `POST /send/text`, `POST /send/media`, `POST /message/downloadmedia`.
* A documentação oficial do Go enfatiza que não há JWT/cookie/login tradicional, e distingue explicitamente chave global de token de instância ([authentication.md](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/docs/wiki/conceitos-core/authentication.md)). O Worker deve resolver internamente `connectionId -> token` e nunca aceitar token ou nome de instância vindo do cliente MCP.

### Rotas para as ferramentas essenciais

* Conexões/status: `GET /instance/all` (global/admin; retorna todas), `GET /instance/status` (token da instância), `POST /instance/connect`, `GET /instance/qr`, `POST /instance/pair`, `POST /instance/disconnect`, `POST /instance/reconnect`, `DELETE /instance/logout`. O novo MCP pode listar apenas conexões já cadastradas no D1; não deve expor `/instance/all` sem filtro de proprietário.
* Contatos: `GET /user/contacts` (lista da instância); `POST /user/info` (body `number`); `POST /user/check` (verificação de existência). A API Go não fornece busca textual/paginação pronta; filtrar nome/número no Worker exige materializar e limitar a lista.
* Grupos: `GET /group/list` retorna `JID`, `OwnerJID`, `GroupName`, `GroupTopic`, `GroupCreated`, `Participants`; `POST /group/info` body `{groupJid}`; `POST /group/participant` tem ações add/remove/promote/demote; `POST /group/create` cria grupo. Para o escopo inicial, somente listar e consultar metadados/participantes.
* Conversas/histórico: a rota é `POST /chat/history-sync`, body `{messageInfo, count}`. Ela solicita ao dispositivo WhatsApp uma sincronização a partir de `types.MessageInfo`; não é uma consulta paginada de mensagens. A lista de rotas não contém `findChats` ou `findMessages`.
* Estado de mensagens: `POST /message/status` body `{id}` consulta a linha persistida; `POST /message/markread` body `{id: string[], number}` marca recibos. `DATABASE_SAVE_MESSAGES=true` é requisito para status, mas o modelo [`pkg/message/model/message_model.go`](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/pkg/message/model/message_model.go) guarda apenas `message_id`, timestamp, status, source e referral; não guarda corpo, direção completa ou mídia. Não existe endpoint de pesquisa/paginação desse histórico.
* Envio: `POST /send/text` usa `TextStruct` (`number`, `text`, `id`, `delay`, `mentionedJid[]`, `mentionAll`, `formatJid`, `quoted{messageId,participant}`); `POST /send/media` usa `MediaStruct` (`number`, `url`, `type`, `caption`, `filename`, quote/menções), aceitando URL JSON, base64 JSON ou multipart; `POST /send/status/text|media` publica status. A resposta `data` contém `MessageSendStruct` com `Info` (ID, chat, sender, `IsFromMe`, `IsGroup`, timestamp e tipo) e mensagem.
* Responder/reagir: `quoted` nos endpoints de envio referencia `messageId` + `participant`; `POST /message/react` usa `{number, reaction, id, fromMe, participant}`. Para o escopo pedido, enviar texto com quote é a resposta.
* Download de mídia: `POST /message/downloadmedia` recebe `{message}` contendo o objeto completo `waE2E.Message` (por exemplo `imageMessage`, `audioMessage`, `documentMessage`, `videoMessage` ou `stickerMessage`), não apenas o ID. O handler retorna `data.base64` como data URL e timestamp. O payload `Message` do webhook pode carregar a estrutura necessária; o Worker deve limitar tamanho e, preferencialmente, gravar em R2 privado/URL temporária em vez de retornar base64 grande.

### Recebimento, histórico e webhook

O backend usa `whatsmeow` e envia eventos por webhook, WebSocket, AMQP ou NATS. Para webhook, `POST /instance/connect` aceita `webhookUrl` e `subscribe` (categorias como `MESSAGE`, `SEND_MESSAGE`, `READ_RECEIPT`, `HISTORY_SYNC`, `GROUP`, `CONNECTION`); a variável global `WEBHOOK_URL` também existe ([events-system.md](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/docs/wiki/recursos-avancados/events-system.md)).

O evento de mensagem emitido é `event: "Message"` (ou `SendMessage`) com `data.Info` e `data.Message`; para grupos pode incluir `groupData`. O código também acrescenta `instanceToken`, `instanceId` e `instanceName` no JSON do webhook ([whatsmeow.go](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/pkg/whatsmeow/service/whatsmeow.go)). O produtor webhook upstream envia apenas `Content-Type: application/json`, faz até 5 tentativas com intervalo de 30 segundos e **não** adiciona assinatura/HMAC ou segredo ([webhook_producer.go](https://github.com/evolution-foundation/evolution-go/blob/9337afc47e10b86cc896a6f432240e40fee95dd1/pkg/events/webhook/webhook_producer.go)). Portanto:

1. Não tratar webhook como autenticado só pelo corpo; o token incluído no corpo é sensível e deve ser removido/redigido imediatamente.
2. Configurar uma URL de callback por conexão contendo um segredo aleatório opaco (por exemplo `/webhooks/evolution/<secret>`) e validar o segredo antes de aceitar o corpo; também conferir `instanceId`/`instanceName` contra a conexão D1. Isso atende à necessidade de um segredo enquanto o Go não oferece assinatura.
3. Deduplicar de forma idempotente no D1 usando `(connection_id, event, message_id)` e tolerar as cinco tentativas upstream; não confiar apenas no cache em memória do Go.
4. Diferenciar no produto “histórico capturado após integração” (webhook) de histórico real anterior: `history-sync` é apenas uma solicitação de sincronização ao telefone e o banco do Go não oferece consulta de conteúdo.

## Decisões recomendadas para a implementação

1. Implementar apenas `POST /mcp` com `@modelcontextprotocol/server@2.3.1`/`createMcpHandler` em modo por requisição, fixando `2026-07-28`; GET/DELETE, `/sse`, WebSocket, stdio e qualquer transporte stateful ficam ausentes.
2. Roteie OAuth, UI e webhook separadamente (Hono opcional), mas não coloque uma página Access HTML na frente de `/mcp`; o endpoint deve responder 401 com Protected Resource Metadata/WWW-Authenticate e o fluxo OAuth deve redirecionar somente no authorization endpoint.
3. D1 deve conter `users`, `connections` (owner, internal ID, friendly name, Evolution instance ID/name, token cifrado, status) e `webhook_events` (dedup key, received timestamp, normalized message metadata). KV fica reservado ao OAuth provider. Nunca retornar `token`, `instanceToken` ou segredo de webhook.
4. Para ferramentas de leitura, buscar contatos/grupos/status pelo token interno resolvido pelo usuário. Histórico deve declarar a limitação do backend: eventos capturados desde o cadastro, e opcionalmente `history-sync` como solicitação assíncrona; não prometer busca retroativa por texto sem uma fonte de conteúdo real.
5. Para mídia recebida, guardar o envelope `Message` mínimo necessário (ou base64 recebido) em R2 privado e devolver handle/URL temporária; limitar bytes e bloquear SSRF ao buscar URLs externas para envio.
6. Testes devem mockar exatamente as rotas Go (`/send/text`, `/send/media`, `/message/downloadmedia`, `/chat/history-sync`, `/user/contacts`, `/group/list`, `/instance/status`) e verificar isolamento por usuário/conexão. Um teste HTTP real só poderá confirmar versão implantada quando URL, `GLOBAL_API_KEY`/tokens e autorização do ambiente forem fornecidos.

## Bloqueio observável

A versão `0.7.2` e os contratos acima são os do commit upstream analisado. Nenhuma chamada controlada ao Evolution Go implantado foi possível nesta coleta porque não havia URL, `GLOBAL_API_KEY` nem tokens no ambiente. Logo não há confirmação da versão em produção, status de instância, webhook ativo ou contrato divergente da instalação real; registrar essa pendência e não inventar resultado.
