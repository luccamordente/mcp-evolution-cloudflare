# Arquitetura

O endpoint público é `POST /mcp`. O Worker cria um servidor MCP e transporte por troca HTTP a cada request. A configuração usada é `legacy: 'reject'` e `responseMode: 'json'`; não existem sessões de transporte, `Mcp-Session-Id`, SSE, WebSocket, stdio, `/sse` ou `createLegacyMcpHandler`.

O protocolo implementado é MCP `2026-07-28`. O SDK v2.3.1 mantém uma constante histórica de compatibilidade para a era 2025, então o Worker publica explicitamente a revisão 2026 no health check e usa a entrada moderna do `createMcpHandler`. Requests MCP devem conter a versão e os cabeçalhos de roteamento exigidos pela revisão (`MCP-Protocol-Version`, `Mcp-Method` e `Mcp-Name`).

O OAuth Provider do Cloudflare é usado no mesmo Worker. Ele responde descoberta, registro compatível, Authorization Code + PKCE S256, refresh e revogação. O recurso canônico é `https://app.wapilot.com.br/mcp`; o hostname `workers.dev` permanece provisório durante a transição. A rota `/authorize` fica sob uma aplicação Cloudflare Access separada, com One-time PIN e allowlist de `luccamordente@gmail.com` e `heitorsalazar@gmail.com`. O Access autentica o navegador; o OAuth Provider emite o token MCP. A assertion do Access nunca é aceita como token MCP.

D1 guarda usuários, conexões, auditoria e eventos de webhook. A conexão padrão é persistida por usuário em `whatsapp_connections.is_default`; estados de onboarding podem permanecer em `whatsapp_connections.connection_state`, mas nenhuma consulta de status usa esse campo como fonte de verdade. `list_connections` consulta as conexões cadastradas no D1 filtradas pelo usuário autenticado; ele não usa o inventário administrativo global `GET /instance/all`, que inclui conexões de todos os usuários. `connection_status` e a UI consultam `GET /instance/status` diretamente no Evolution Go. A primeira conexão recebe o papel padrão automaticamente, a exclusão da conexão padrão promove a conexão restante mais antiga e a UI só altera o padrão por ação explícita. As ferramentas MCP que operam uma conexão aceitam o UUID interno opcionalmente: quando omitido, o Worker exige exatamente uma conexão padrão; um UUID informado tem prioridade. Ausência de padrão ou múltiplos padrões produz erro explícito. KV é reservado ao estado do OAuth Provider. O token de cada instância é cifrado com AES-GCM usando `TOKEN_ENCRYPTION_KEY` em Secret. O Worker resolve `(user_id, connection_id)` antes de descriptografar o token e enviar `apikey` ao Evolution Go.

`/connections` é a superfície autenticada do dashboard e do onboarding. Os endpoints same-origin `/connections/data`, `/api/connections/provision`, `/api/connections/:id/status`, `/api/connections/:id/qr` e `/api/connections/:id/default` sustentam a troca de contexto, o provisionamento, a renovação do QR e a verificação do estado sem expor tokens de instância. Depois de um logout, a renovação chama `POST /instance/connect` na instância existente e consulta `GET /instance/qr` até o provedor publicar o novo código; não cria uma segunda conexão nem usa `connection_state` do D1 como estado live.

No carregamento de `/connections/data`, cada conexão consulta `GET /instance/status` diretamente no Evolution Go. Quando o status informa uma conta conectada, a mesma leitura consulta `POST /user/avatar` com o token da instância para obter a foto e usa o `name` do status como display name. Se o status não trouxer o JID, a camada interna tenta `GET /instance/info/:instanceId` com a chave global apenas para descobrir o número; essa resposta nunca é repassada ao navegador e suas credenciais são descartadas.

O alias legado `/admin/evolution` redireciona para `/connections?provision=1`, porque o Cloudflare Access protege a aplicação `/connections`. O redirecionamento garante que o navegador passe pelo desafio Access antes de entrar no fluxo de provisionamento restrito ao administrador.

A mesma superfície Access de `/connections` expõe `GET /connections/authorizations` e `DELETE /connections/authorizations/:id` (com `POST /connections/authorizations/:id/revoke` como alias), usados pelo dashboard para evitar uma troca de audiência durante `fetch`. Os endpoints equivalentes em `/api/authorizations` permanecem como compatibilidade para clientes da aplicação Access separada de `/api`. A listagem consulta os grants do usuário autenticado no OAuth Provider, remove grants expirados, pagina por cursor e devolve somente nome do cliente, escopos, datas, recurso e host de redirect redigido. A revogação sempre usa o par `(grant_id, user_id)` fornecido ao Provider; depois do sucesso, a UI recarrega a lista do Provider e só confirma a desconexão quando o grant não aparece mais. A aprovação OAuth mantém `revokeExistingGrants: false`, portanto clientes autorizados podem coexistir e cada grant é revogado individualmente. A assertion Access continua separada do bearer OAuth aceito em `/mcp`.

`list_messages` consulta diretamente `GET /message/search?q=&limit=`. Essa busca depende de `DATABASE_SAVE_MESSAGES=true` no Evolution Go e não substitui uma listagem de chats: o fork não expõe endpoint de listagem de chats. O webhook continua recebendo eventos para integração e auditoria operacional: usa um segredo opaco por conexão, verifica a instância, remove o token do payload e deduplica por `(connection_id, event_name, message_id)`.

O cliente em `src/lib/evolution.ts` fala exclusivamente o documento JSON:API 1.1 do Evolution Go: requests com `data` e `type`/`id`/`attributes`/`relationships`, `Accept: application/vnd.api+json`, e respostas com recursos `message`, `connection` ou `chat`. A camada interna converte `attributes.at` (milissegundos JavaScript), `attributes.body`, `attributes.encodingFormat`, `relationships.author` e `meta.chat` para os tipos MCP sem consultar envelopes antigos como `data.items`, `message_id`, `timestamp`, `status` ou `raw`. Webhooks exigem `jsonapi.version` `1.1` e `meta.instanceId`/`meta.event`; o `instanceToken` é removido antes da persistência, inclusive quando o documento contém uma coleção de mensagens.

O provisionamento envia somente `name` e `token` ao criar uma conexão e grava o `data.id` retornado pelo Evolution Go como `instanceId` canônico. Em execuções administrativas posteriores, a conexão cadastrada também é reencontrada pelo nome amigável para evitar duplicação quando o UUID remoto tiver sido gerado pelo provedor.

Antes de qualquer resposta estruturada de ferramenta MCP, o Worker percorre recursivamente os valores JSON. URLs de `https://storage.neurau.com.br/attachment-storage-production/evolution-go-medias/<arquivo>` são reescritas para `https://media.wapilot.com.br/r/<arquivo>`, mantendo a query original sem reconstruí-la. O hostname e o caminho do provider nunca aparecem no payload MCP. O hostname público é atendido pelo mesmo Worker: `GET` e `HEAD` em `/r/<arquivo>` redirecionam para o caminho original e mantêm somente `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-SignedHeaders` e `X-Amz-Signature`; parâmetros acrescentados pelo cliente, como `utm_source`, são removidos antes do redirect para não invalidar a assinatura.
